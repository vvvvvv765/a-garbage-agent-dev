> 对象：`spirit/`（Spirit 本体，**2026-11-18 基线**）
> 配套：[Agent 项目构思](Agent项目构思.md)（思想层）；[体系总表](体系总表.md)（目标结构，已按它落地）。

## 一、分层与依赖

```text
主板（MoBo / Engine）
  装配：BIOS → 恢复会话 → 能力上总线 → 渲染起线程 → CPU 开机

BIOS（AgentStart）        → 配置 / 信息表 / 异常 / 日志
信息表（Bus）              → CPU 的子体系（布尔 + 指令）
协议（Contract）           → 信息表里放什么：Contract / ThinkingControl / Instruction

CPU（DC）                  → 唯一调度者
  子体系：Reconnect（重试）
  调（句柄，主板注入，CPU 不 import 具体体系）：
      GPU.request / mem.consume / mem.save / mem 读表 / 能力（总线句柄）/ 用户输入
  对渲染只下发指令（信息表）

内存（Memory）—— 数据表
  子体系：Persist（落盘 / 恢复）、ModO（模型侧入口）、地址词表
  对外门面（给 CPU 的同步口）：consume(stream) / save()
  瞬态地址：stream（不 seq、不落盘、轮末清空）

GPU（对模型）—— 给大模型看的
  子体系：ModI（发送）、Summary（摘要）
  读数据表 → ContextBundle → 交给 ModI

渲染（对人）—— 第二个 GPU
  子体系：控制台出口、Web 出口
  常驻线程；CPU 指令启停；自己读数据表

能力（Capabilities）—— 每个能力是它的子体系
用户输入（UserInput）—— 控制台源 / Web 源
异常（Faults）—— 每个体系自带 handler（不构成体系）
日志 / 配置 —— 主板设施

Provider（Adapter）—— 共用方言，不属于任何体系
轮次号（Turn）—— 中立工具：进程内递增；CPU 边界 begin()，日志 / 审计 / 用量 / 渲染只读
```

**无循环导入。** 唯一要小心的点：`Memory/Persist.py` 不进 `Memory/__init__.py` 导出——
它 import `Faults`，而 `Faults` import `Memory`，从包初始化导出会成环。使用方写 `from Memory.Persist import persist`。

文件类能力都声明 `deps=("workdir",)`；搜索自动跳过 `.git` / `.venv` / `node_modules` / `__pycache__` / `shell` 等重目录；明显二进制的文件直接拒绝。

### browser：ego lite（2026-11-21）

- **定位（他强调的整机观）**：能力体系是这台 Agent 计算机的**外设层**，不是“内核之外再加的功能”。文件、进程、网络、浏览器都是外设；ego lite 就是这台计算机的**浏览器设备**。内核的取消 / 超时 / 隔离 / 审计 / 落盘，最终都是为外设服务的。所以接浏览器不能只做成“包一层 CLI”，要按设备来考虑：发现、健康、生命周期、归属、观测、信任边界、故障降级。
- **形态**：一个代码型能力。模型传 `code`（Node ESM，顶层 await 可用），能力把脚本从 **stdin** 喂给 `ego-browser nodejs`；不拼 shell，Windows 无引号问题。`guide=true` 返回当前安装版本的 `ego-browser skill` 指南。
- **启动器定位**：`engine.ego_browser` → `SPIRIT_EGO_BROWSER` → `PATH` → Windows `C:\Program Files\Citro Labs\ego lite\Application\<版本>\ego-browser.exe`（按目录 mtime 取最新）→ 便携自带 `_internal/shell/ego-lite/ego-browser.exe`；都找不到时回“没装 + 下载地址”。
- **会话 Space**：prelude 注入 `spiritTask()`，按 `数据根/browser/<spirit-session>.space` 记录 spaceId 并复用；每个 Spirit 会话固定一个 Space，两个会话并行不抢页面。`SPIRIT_SPACE` 同时注入给模型。
- **截图**：模型用 `spiritShot(page, {path:"绝对路径.png"})`；脚本结束在 finally 打印 `__SPIRIT_IMAGES__[...]`，能力摘掉标记、把图按内容哈希复制进 `uploads/`，作为 `CapabilityResult.images` 走现有图像通路。单图 ≤8MB。
- **信任/超时**：`side_effect=external`、`trust=untrusted`（网页内容按不可信处理）；默认 120 秒，可用 `timeout` 调到 600；取消/超时杀进程树并带回已捕获输出。
- **失败可见（2026-11-21 同批）**：`CapabilityResult` 新增 `ok`；浏览器脚本非零退出、超时、缺 CLI 都返回 `ok=False`，界面 / 日志不再把失败显示成“已返回”，CPU 会自动补 `失败：` 前缀。
- **权限接管（同日）**：脚本输出里有 `permission prompt` / `user now controls` / `takeOverTaskSpace` 时，能力写 `browser/<session>.handoff` 标记并返回“等用户处理完、重跑同一段脚本”；下次 `spiritTask()` 看到标记先 `takeOverTaskSpace(spaceId)` 再继续，成功后删标记。设置页状态会显示「等待你在浏览器里处理权限弹窗」。
- **视频状态（同日）**：prelude 提供 `spiritVideo(page)`，读 `paused / ended / currentTime / duration / readyState / muted`；提示词要求用它判断“是否真的在播”，不许靠截图猜。脚本 `finally` 还会自动打印 `__SPIRIT_PAGE__`（标题 / URL / 视频状态），能力解析后追加一行 `[页面] …`，模型不必再单独 evaluate 查询。
- **调用次数**：提示词与工具描述明确“一次脚本做完多步（goto → 等加载 → 取信息/截图）”，减少像腾讯视频那轮 9 次小调用的情况。
- **安装前提**：ego lite（Windows beta）需要完成一次 GUI onboarding；没完成时 CLI 会返回提示，能力原样带回给模型。
- **测试**：`spirit_browser_test.py` 用假 CLI 测脚本 / 指南 / 超时 / 截图附件 / 缺 CLI；`spirit_browser_live_test.py`（名字带 live，离线回归跳过）在真实 ego lite 上打开 example.com、截图进上传区、第二次调用复用同一个 Space（`SPACE:2 | PAGES:1`）——已通过。
- **设备化（2026-11-21 同批补完）**：
  - **健康**：`/api/kernel` 带 `browser.health()`（安装 / 路径 / 应用是否在跑 / onboarding，onboarding 检查后台刷新、20 秒缓存）；设置 → 通用新增「浏览器（ego lite）」一行，显示就绪状态、CLI 路径、当前 Space / 页面 / 最近截图，带「检查」按钮。
  - **生命周期**：首次执行 browser 时若 ego 没在跑，`start_app()` 拉起应用并等最多 15 秒；**不替用户关闭共享浏览器**。Spirit 关机时 `dispose()` 调 `release_spaces()`，对每个 Spirit 用过的 Space 执行 `finish({keep: []})`（只关 agent 建的页面，不动用户标签页），成功后删 space 记录文件。
  - **观测**：`/api/browser?session=` 返回当前会话的 `space {space, pages, url, title}` 与 `last_screenshot {path, upload, at}`；截图时写 `数据根/browser/<session>.last.json`。
  - **信任**：浏览器的结果 meta 里 `source = "browser（网页内容）"`；不可信内容之后的审批 / 阻止提示会显示这个来源；设置页仍可调「仅审计 / 确认 / 阻止」。
  - **便携自带（2026-11-21）**：ego lite 的 `Application` 目录（约 621MB，含启动器 `ego.exe` 和 `<版本>/`）放在 `spirit/shell/ego-lite`，`make-portable` 拷到 `_internal/shell/ego-lite`；能力按 `ego-lite/ego-browser.exe` 和 `ego-lite/<版本>/ego-browser.exe` 两种布局查找。启动器在 `ego-browser.exe` 的上一级或上两级找 `ego.exe`。查找顺序：配置 → `SPIRIT_EGO_BROWSER` → PATH → 系统安装 → **便携自带副本**；有系统安装时优先用系统安装（保留用户真实登录态 / onboarding），没有时用自带副本（新 profile，首次需 onboarding）。绿色版体积因此约 1.4GB。
  - **强杀补清理（2026-11-21）**：每次开机后台跑 `cleanup_stale_spaces()`，只释放 **30 秒前** 的 Space 文件（避免误伤刚创建的）；`release_spaces()` 对每个记录执行 `finish({keep: []})` 后删记录。强杀时应用还在跑也没关系，下次启动会补。应用不运行时跳过，保留记录等下次。

新能力带两个依赖：`dnspython`（`dnsLookup`）与 `PyYAML`（`parseData`）；已写进 `pyproject.toml`，PyInstaller 加了 `--collect-submodules dns / yaml`。

### 能力体系的三个契约

| 契约 | 方向 | 路径 |
|---|---|---|
| **说明**（模型怎么知道它） | 能力 → 模型 | `CapabilitySpec`（name / description / parameters；`side_effect` / `trust` / `timeout` 不进模型 schema）→ `Registry.schemas()` → `GPU/ModI.py` → `Provider/Adapter.py` 的 `tools` 字段 |
| **输入**（模型怎么给参数） | 模型 → 能力 | `function_call.arguments`（JSON 字符串）→ `ModO` 写 `tool_call` → **CPU 读表** → `CapabilityInput`（解析 + 校验）→ `run(arguments)` |
| **返回**（结果怎么回去） | 能力 → 模型 | `run()` 返回 `str`（或带 `meta` 的 `CapabilityResult`）→ `CapabilityOutput` → 截断 / spill → 写 `tool_output` → GPU 下一轮配对成 `function_call_output`；`meta.images` 会按方言转成图像内容 |

注册表（`Capabilities/Registry.py`）负责：

- **加载**：`register(obj)`，或清单条目 `{"module", "class", "config"}`；内置能力也走同一条路
- **生命周期**：`configure(config)` / `setup(deps)` / `dispose()`
- **启停**：`enable` / `disable`——停用的不出现在 `schemas()`，也不能执行
- **校验**：必填 / 类型 / 多余字段（`Capabilities/Validate.py`）
- **调度**：`CapabilitySpec.side_effect` = `read` / `write` / `external`，决定批内是否并行；也用来判定只读审批
- **超时**：`CapabilitySpec.timeout`（秒），没写就用 `engine.capability_timeout`（默认 60）；超时只代表**不再等它**——Python 线程不能强杀，子进程类能力请自己设 kill 超时（bash 就是 30s 自杀 + 体系 40s 兜底）
- **异常**：每个能力一个独立 handler（记录里是 `capability:<名字>`）；能力自己也可以声明 `deps=("faults",)` 主动上报

### 场景（2026-11-18）

- 目录：`Scenarios/<id>/scenario.json` + `prompt.md`；现有 `daily` / `pentest`
- **共享能力（2026-11-21）**：`Scenarios/common.json` 列所有场景都有的能力（文件 / 进程 / todo / 网络 / 解析 / 打包 / `browser`）；`Scenarios.capabilities_for(id)` 返回 **common ∪ 场景清单**（去重保序）。`scenario.json` 的 `capabilities` 只写“这个场景额外要的”。主会话的 `apply_scenario` 和额外会话的 `CapabilityScope` 都走同一个并集入口。当前：daily 额外 = `dnsLookup` / `httpProbe`；pentest 额外 = `sandboxRun` / `dnsLookup` / `portScan` / `httpProbe`。
- **提示词**：GPU 每轮拼 `Prompts/engine.md` + 场景 `prompt.md`（增量，不复制底座）
- **能力子集**：`capabilities` 是白名单；`Engine.use_scenario()` 通过注册表整体启停（使用并集，不是 scenario.json 的单项）
- **安全默认值**：`defaults` 写配置（approval / sandbox.workspace_only / max_steps 等）

### 持久 shell 的竞态（2026-11-21）

- **现象**：bash 超时后下一次调用偶发返回“shell 已退出（可能执行了 exit），下次调用会重开”，实际命令根本没跑。
- **根因**：超时会 `stop()` 杀旧 shell；下一次调用 `_start()` 新建 shell 后，旧 reader 线程的 `finally` 晚到，把共享的 `__closed` 又置成 True，新 shell 被误判为已退出。
- **修复**：reader 的 `finally` 只在自己仍是当前进程时置 `__closed`（`if self.__proc is proc`）。`spirit_tool_hardening_test.py` 连续跑 3 次稳定通过。

### 硬盘体系（2026-11-19 批 Q）

- **定位**：agent 计算机的**存储主体系**，和内存并列。内存放当前轮次要进上下文的热数据；硬盘放冷数据——会话、工作区、工具落盘的大结果、日志、沙箱目录。模型通过能力按需读取，不默认进上下文。
- **区域**（每个区域在磁盘上就是一个文件夹，能力只认区域）：
  - `workspace`：工作区（子体系），作业文件的落点
  - `artifacts`：**能力产物区**（`Artifacts/`，工作区之外），工具落盘的大结果；框架托管，可整体清理
  - `sessions`：会话文件（`Session_Storage/`）
  - `logs`：日志 / 审计
  - `sandbox`：`sandboxRun` 的临时工作目录
  - `uploads`：用户上传的图片
- **不可删除**：主体系之一，没有注销入口；开机 `disk.ensure()` 必须成功，UI 只提供"看用量 / 打开文件夹 / 清能力产物 / 删会话"这几样接口。
- **区域所有权（2026-11-20 他定）**：`workspace` = 作业文件（模型读写 / bash cwd / 交付物）；`artifacts` = **能力体系的落盘产物**（`数据根/Artifacts`，**不在工作区里**，框架托管、可整体清理，沙箱单独放行让模型按 `meta.path` 读回）；`sessions` / `logs` = 框架自身数据（受保护）；`sandbox` = 隔离执行临时区；`uploads` = 用户上传。
- **冷热规则**：能力输出超过 inline 阈值 → `Disk.artifact()` 写进 `数据根/Artifacts/spill/`，返回摘要 + 路径 + 大小；模型需要时用 `readFile` 继续读。这取代了原来散落在 `tmp/spill` 的做法（`engine.spill_dir` 显式配置仍兼容）。
- **UI**：设置 → 硬盘，显示六个区域的占用 / 文件数，可打开对应文件夹、清理能力产物；会话删除仍走会话菜单，但由硬盘体系校验路径。

### 沙箱与审计脱敏（2026-11-18）

- **策略层**（`Capabilities/Sandbox.py`）：
  - 文件能力：**默认不再限制工作区**（工作区只是落点）；配置、会话、日志、`~/.ssh` / `~/.aws` 等机器数据永远拒绝；symlink 按真实路径；`deny_paths` 可选追加
  - bash / `processStart`：cwd 固定工作区；环境清掉 Key / `SPIRIT_*` / 云凭据，`HOME` 指到工作区；**命令灾难闸**（见下）
  - CPU 执行前调 `capabilities.precheck()`：拒绝的调用不进入审批，直接回工具结果
  - **工作区外访问（2026-11-19 批 P）**：范围菜单里一行「工作区外访问」——`自动允许`（默认，= `workspace_only=false`，不设边界）⇄ `仅工作区`（= `workspace_only=true`，越界弹授权卡，可用 K 的允许本次 / 本次运行）。旧的设置页开关和可访问路径入口已移除。
  - **默认工作区（2026-11-19 起）**：没有显式配置时是 `数据根/workspace`，不再回落到启动目录
  - **命令灾难闸（2026-11-19 他的设计）**：只拦**会把机器搞坏**的命令——格式化 / 分区（`format` / `diskpart` / `mkfs*` / `fdisk` / `wipefs`）、引导与卷影（`bcdedit` / `bootrec` / `vssadmin` / `wbadmin`）、`dd` 写块设备、目标为磁盘根 / 系统目录 / 用户主目录根 / 机器数据 / 工作区根目录本身 / Git Bash 根、fork bomb。命中 = 直接拒绝。**其它命令一律放行**（工作区外删除、批量删除、`git clean`、下载后执行、结束进程、注册表、解释器内联代码都不拦）。诚实边界：模式识别挡常见灾难和手滑，挡不住变量拼接 / 编码 / 写脚本再执行。
  - **CONFIRM 分级只作诊断，不接审批**（2026-11-20 明确）：判定器内部会把“越界删除 / 内联危险原语 / 下载执行”标成 confirm，但执行层只对 DENY 拒绝。按《Agent项目构思》§〇「能力优先，不过度限制」，宁可少问一次，不做保姆；要扩成审批层得单独拍板。
  - **引擎数据路径检查是按字面路径匹配的**（`check_command` 里的子串扫描）：`cd` 进去只写文件名、`%20`、通配符都不拦——**这是有意的边界**，它防的是“手滑把 config / 会话 / 日志路径写进命令”，不是通用沙箱。别再往上加“敏感文件名在任何位置出现都拦”这类规则：会挡住正常任务，违背能力优先。
- **隔离沙箱 = `sandboxRun` 能力（2026-11-19 批 O）**：WSL + bubblewrap 的一次性环境——只把 `数据根/Sandbox` 挂到 `/work`，系统目录只读，`/mnt` / `/home` / `/root` 不可见，`/tmp` / `/run` 是临时盘；默认 `--unshare-net`，`network=true` 才联网；默认超时 120 秒。`side_effect=read`（不触发审批、批内可并行）。**模型自己决定何时用**：来源不明的脚本、下载的代码、靶场 payload 用它，普通任务直接用 `bash`。共享 Linux 内核，不是虚拟机。
- **bash 对引擎数据有围栏**：命令里出现配置 / 会话 / 日志的路径（或工作区=数据根时的文件名）直接拒绝；其它路径仍受「policy 不是 VM」的诚实边界限制。
- **spill（2026-11-19）**：默认落在 `工作区/tmp/spill`（会话目录受保护，模型读不回来）；旧默认值 `Session_Storage/spill` 视同未配置。
- **不是 VM**：写脚本再执行等花招拦不住；OS 级隔离（bwrap / Docker）评估后暂不做，`backend` 接缝保留
- **脱敏**：`Redact/` 在审计和工具调用日志落盘前打码（sk-* / gh*_ / AKIA / Authorization / api_key / password，以及当前 Key 原值）；审批弹窗看原文。

### 真实用量 / 成本 / 预算（2026-11-18）

- **来源**：provider 的 `response.completed` 里有真实 `usage`；`Provider/Adapter.usage()` 取 input / output / cached / reasoning。
- **账本**：ModO 每次对话请求写一条 `usage`；Summary 每次摘要请求也写一条（`purpose: summary`）。记录含模型 / 提供商 / token / 成本 / 是否计价 / 币种。
- **计价**：提供商配置 `pricing: {input, output, currency}`（元 / 百万 token，`cached_input` 可选，默认按 input 价）。`Usage/` 是中立纯函数，不写表。
- **预算硬停**：`DC/Guard.py` 在每次请求模型前检查（本轮 / 会话的 token 与成本）；超了写异常记录并结束这一轮，不再请求模型。配置：`engine.max_turn_tokens` / `max_session_tokens` / `max_turn_cost` / `max_session_cost`。
- **重复调用**：同一 `(能力名, 参数)` 达到 `engine.repeat_limit`（默认 3）后，CPU 不再执行，直接回一条“重复调用已拦截”的工具结果；`processOutput` / `processList` 轮询豁免。
- **显示**：`Engine.usage()` / `GET /api/usage`；前端统计条显示真实 token、成本、上下文占比，标题里有输入 / 输出 / 缓存 / 预算明细。
- **上下文构成**：GPU 每次出包估算三块（系统提示词 / 工具定义 / 对话消息），有真实 `input_tokens` 后按比例校准；`Engine.context()` / `GET /api/context`；前端点统计条里的百分比弹出明细（`spirit_context_ui.js` 截图核对）。

### 信号语义：边沿 vs 电平（2026-11-18）

- **边沿**（渲染 start / stop）：`Instruction` 不可变，CPU 追加到 `InstructionQueue`；渲染按 `seq` 逐条消费，stop 先 drain 再关，start 再开。轮次边界不回执、不等待。
- **电平**（思考开关 / effort / 审批模式）：最新值生效，旧值过期，不需要 seq。
- **真同步点**（关机 / 切会话）：`Render.sync(timeout)` 有界排空；不是每轮握手。
- stream 片段带 `epoch`，旧轮次不画。

### 可中断等待 / 持久 shell（2026-11-18）

- **取消令牌**（中立 `Cancel/`）：CPU 置位；ModO 模型流、Summary 摘要、FetchUrl 分块读都检查；`Engine.interrupt()` / `Engine.stop()` 一次取消流 + 工具 + 挂起审批 + 摘要。
- **审批取消**：`Engine.set_approver(fn, cancel)`；Web 的 cancel 会拒绝挂起的审批队列。
- **渲染 epoch**：CPU 的 `Instruction.seq` 每轮 +1；ModO 的 stream 片段带 `epoch`；渲染只画本轮，旧轮次残留跳过。stop/start 不再靠“大概画完了”。
- **持久 shell**：`Capabilities/Shell.py` 起一个 `bash -s`，命令之间 `cd` / `export` / `source venv` 保留；取消 / 超时 / `exit` 杀树重开；并发 bash 串行。
- **边界**：取消硬、渲染回执软；CPU 不等渲染排空。

### 执行生命周期（能力体系的子体系）

`Capabilities/Executions.py` 记每一次在飞调用：`call_id`（trace id）/ 名字 / 开始时间 / 截止时间 / 取消事件 / 子进程。

- **停止**：`Engine.interrupt()` / 页面停止 → CPU 让能力主体系 `cancel_all("用户停止")` → 在飞执行置取消、杀进程树；等待循环每 0.2s 看一次取消，**不再等满能力超时**；本轮直接结束，不再请模型续写。
- **超时**：执行子体系按 `spec.timeout` / `engine.capability_timeout` 判定，取消 + 杀进程 + 回 `ok=False`。
- **协作**：子进程用 `executions.track(proc)`（bash 已接）；长循环用 `executions.check()`（搜索 / 找文件 / 翻会话 / 抓取已接）。
- **诚实边界**：Python 线程不能强杀；纯 Python 死循环只能等它走到检查点，线程池槽位在退出前仍占着。
- **观测**：`Engine.running()` / `GET /api/running` 返回 `{call_id,name,elapsed,timeout}`；前端轮次头显示“正在处理… bash · 3.2s”。

### 安全（审批 + 审计）

模型是操作员，但**动真东西之前要经过用户**——照 Claude Code 的权限确认做的最小版。

**2026-11-19 拆成两个正交的轴**（原来的「工作区内修改 / 每次确认 / 完全放行」把范围与问不问混在一起）：

| 轴 | 值 | 行为 |
|---|---|---|
| 范围 `engine.access` | `workspace`（默认，可修改） | 允许写，路径受沙箱限制 |
| | `readonly`（查看） | `write` 类**直接拒绝、不弹审批** |
| 模式 `engine.approval` | `ask`（默认） | `write` 与 `external` 要问；`read` 放行 |
| | `auto` | **完全自动**：都不问；不可信内容之后也只留审计（2026-11-20 他定）。「不可信内容之后：阻止」是显式策略，仍然生效 |

- 旧值兼容：`manual` / `rules` → `ask`，`auto` → `auto`。
- 判定顺序：沙箱（越界 → 先弹访问授权，允许本次 / 本次运行；禁止路径直接拒绝）→ 范围（查看且写 → 拒绝）→ 不可信策略（block → 拒绝）→ 模式（auto → 放行）→ 只读（放行）→ 问。刚在访问授权里被允许的调用不再重复问。
- **界面**：输入栏两颗 chip——「可修改 / 查看」和「询问 / ⏵⏵ 自动」；`Shift+Tab` 在询问与自动之间循环，自动时输入框上方显示 `⏵⏵ 自动模式已开启`。
- **只读来源**：`CapabilitySpec.side_effect`（`read` / `write` / `external`）。Security 通过 Spirit 注入的 `capabilities.side_effect(name)` 判定，未知能力按 `write`；硬编码 `READONLY` / `EXTERNAL` 只作兜底。
- **问** = `Engine.set_approver(fn)` 接进来的回调；`fn(request) -> bool` 或 `(bool, reason)`；访问授权可回 `(bool, reason, "session")`。
  - Web：`WebUI/server.py` 的 `_approver` 推 `approval_request` 事件，页面出**审批卡片**（允许 / 拒绝），`POST /api/approval {id, allow, remember}` 答复（`remember=true` = 本次运行都允许）；超时按拒绝。「工作区外访问」用同一通道，卡片带 `kind=access` / `path` / `reason`，走三个按钮。
  - CLI：`MoBo/main.py` 的 `_console_approver` 调 `UserInput/Console.py` 的 `ask()`，打印 `[审批] 能力 + 参数`，问 `[y/N]`。**stdin 只有 Console 的读线程一个属主**：读到行时若有待审批，这行是审批答案；否则进用户消息队列。用户先敲的消息不会被审批吃掉，审批答案也不会变下一条消息。
  - 没接回调：拒绝（安全默认）。
- **拒绝的落点**：CPU 在调能力体系**之前**判定；拒绝的调用不进线程池，直接作为 `CapabilityOutput(ok=False)` 写 `tool_output` 回给模型（业务结果，不惊动 CPU）。
- **本地控制面（2026-11-19）**：`/api/*` 需要 `X-Spirit-Token`（页面加载时由服务端注入 meta，前端 fetch 包装自动带；SSE 用 `?token=`），Host 必须是本机（防 DNS rebinding）；`/api/status` 豁免（桌面壳靠它判断起没起）。导出供应商要显式 `confirm:true`；会话 load/rename/delete 的 path 必须落在会话目录内。测试用 `WebUI.server.test_client()`（自动带令牌）。
- **审计**：每次判定追加一行 `Logs/audit.jsonl`（时间 / 能力 / call_id / 参数摘要 / 是否放行 / 理由），同时进 Spirit 日志。
- **停止 / 中断**：挂起的审批一律按拒绝收掉（前端卡片会显示“已停止”）。

## 三、三条流

- **控制流**：CPU → 信息表（`Contract` 布尔 + `Instruction` 指令）→ 各体系读
- **报告流**：各体系 → 信息表（`Contract(SI=...)`）→ CPU 读
- **数据流**：生产者 → 数据表 → 消费者自己取

```text
              大模型
            ▲       │
      ModI  │       │  ModO
      (GPU) │       │  (内存)
            │       ▼
          数据表 ◄── 用户输入 / 能力 / 异常 / 摘要
            │
            ├──► GPU：读出来加工成消息包
            └──► 渲染：实时看 stream，回放看持久记录
```

**CPU 不搬数据**：本轮新增的 `tool_call` 由 CPU 读表取（`mem.records_after(水位)`，按 `call_id` 去重）。

## 四、启动 / 关机

```text
Engine.start()
  1. client.Create()              # BIOS：自检 + 句柄进表 + 报告 SI
  2. persist.restore_latest()     # 恢复最新会话（engine.restore；内存非空则跳过）
  3. NT.register(TOOLS, tools)
  4. render.start()               # 显示线程从数据表当前末尾开始看
  5. DC.boot()                    # 注册 CPU_USER / CPU_MOD / CPU_THINKING / CPU_RENDER；检查 BIOS
Engine.run()
  → DC.run()                      # 主循环
  finally: render.shutdown()
DC.run() finally: 能力池 shutdown → persist.save() → mem.stop()
```

入口：`python -m MoBo.main`（控制台）/ `python -m MoBo.main web`（浏览器）。

### 控制台输入（CLI 专属）

`UserInput/Console.py` 是进程里**唯一读 stdin 的地方**（daemon 读线程，只搬原始行，不写表、不下指令）：

- `console.read(prompt)`：接给 `UserInput` 当输入源；阻塞等用户消息队列。
- `console.ask(request, timeout)`：接给审批出口；注册唯一 pending，打印审批提示，等答案。
- `console.cancel_pending()`：停止 / 中断 / 关机时叫醒挂起的审批（按拒绝收）。
- 路由规则：读到一行时**有 pending 就是审批答案，没有就进消息队列**；超时 / 取消之后迟到的行按用户消息处理，不补写答案；EOF 之前已排队的消息会先读完（EOF 哨兵在队尾），`printf 'exit\n' | spirit` 不会丢最后一行。
- `Ctrl+C`：`MoBo` 装 SIGINT handler——审批中 → 拒绝 + 中断本轮；空闲等输入 → 作废当前行（限时）；流式 / 工具中 → 中断本轮；两秒内第二次 → `console.close()` + `Engine.stop()` 退出。
- **关机收尾**：`MoBo` 在 Spirit 收尾后调 `os._exit`。读线程是 daemon，可能还阻塞在 `input()` 上；正常解释器收尾会和它抢 stdout 缓冲锁（`_enter_buffered_busy`）。日志和输出先 flush，再退出。
- **诚实边界**：终端是行模式，审批提示可能插在用户正在敲的半行后面；Ctrl+C 的“作废”是逻辑丢弃并重提示，不清屏。Web 模式不走 Console（输入来自 HTTP 队列），没有这个问题。

## 六、并发

| 执行流 | 是谁 | 形态 |
|---|---|---|
| 中心流 | CPU | 单线程 |
| 数据流 | 内存 | 1 worker + FIFO + 条件变量 |
| 执行流 | 能力 | 线程池 4；批内有写 → 整批串行 |
| 显示流 | 渲染 | 1 常驻线程 |
| 网络流 | Web | Flask 多线程 |

- 渲染靠 `mem.wait_revision()` 等新数据（条件属于表，不属于任何体系）。
- `stream` 瞬态：ModO 写、渲染读，独立锁，不走 seq 队列。
- **批内调度**：`CapabilitySystem.run` 按 spec 的 `side_effect` 分流——批内有 `write` 就整批串行（每项前查取消令牌），全 `read` / `external` 才并行。这样同一批工具的读写顺序可推演，也避免持久 shell 同批抢锁。

### 图片输入（多模态，2026-11-20 批 Z）

- **一条线到底**：`上传` → 硬盘 `uploads` 区 → 用户输入 `{text, images:[{id,mime}]}` → 内存 → GPU 组装 → Provider 三种方言。

- **磁盘回放 + 稀疏行偏移索引**：回放窗口要翻到冷区时，`history_window` 从磁盘把原文读回来，和内存热记录按 seq 去重合并。
  - sidecar 里记 `lines` 和 `anchors`（每 512 行一个字节偏移）；`Persist.read_records(limit_turns)` 从最近锚点 `seek`，先读尾部一段，用户轮数不够再往前扩，**不再整份解析**。
  - 老文件没有索引：第一次读时扫一遍建锚点（只算偏移，不解析 JSON）；追加 / 改名同步更新行数与锚点。
- **用量不丢**：`Engine.usage()` 改用 `mem.view(usage)` + 显式的 `last_user`，退役不影响会话累计；`Guard` 本来就走视图。
- **已知边界**：`history_events()` 是“热记录视图”（旧接口 / 测试用）；真正的完整回放走 `history_window`。
- **回归**：`spirit_af_cold_test.py`（退役边界 / 用量完整 / 新编号 / 磁盘回放 / 懒加载）、`spirit_persist_index_test.py`（索引写入 / 区间读 / 全量读 / 追加更新 / 老文件建索引）。

### 实例路径：Spirit 不猜（2026-11-18）

Spirit 只提供机制，**数据放哪、工作区是哪，由实例决定**：

```python
engine = Engine(home=r"Companion\data", workdir=r"Companion\workspace")
```

| 参数 | 决定 | 不传时 |
|---|---|---|
| `home` | 数据根：`config.json` / `Session_Storage` / `Logs` / spill / audit 全在它下面 | `SPIRIT_HOME` 环境变量 > 项目目录（源码）> `%LOCALAPPDATA%/Spirit` |
| `workdir` | 能力执行 cwd、文件能力相对路径、提示词里的“工作目录” | 配置 `engine.workdir` > 启动目录 |

- 构造时做的事：设数据根 → **按新根重读 `config.json`** → 重新绑定日志 / 会话目录 / 审计 / 能力依赖（`Log.rebind`、`Persist.rebind`、`Capabilities.rebind`、`DC.refresh_config`）。
- 所以不用再关心 import 顺序；同一进程里换实例也成立（新 `Engine(home=...)` 会整体重绑）。
- 子进程模式（桌面壳拉起 Python）用环境变量：`SPIRIT_HOME`（数据根）、`SPIRIT_WORKDIR`（工作区）、`SPIRIT_WEB_HOST` / `SPIRIT_WEB_PORT`（网页入口）；`SPIRIT_SESSION_DIR` / `SPIRIT_LOG_DIR` 仍可单独覆盖。
- **首次脚手架归应用**：建 `data` / `workspace`、写默认 `config.json`。Spirit 只会在自己要写的时候创建目录。
- 目标目录布局（桌面版）：`engine/`（程序，可整体替换）+ `data/` + `workspace/` + 应用壳。

### 模型提供商与工作区（2026-11-18）

**提供商**存 `llm.providers`，顶层 `llm.*` 是当前生效值；Key 优先 `llm.api_key`，空才读 `llm.api_key_env`（兼容旧用法）。**接口类型** `kind`：`openai`（OpenAI Responses）、`openai-chat`（Chat Completions）、`anthropic`（Anthropic Messages）。**认证方式** `auth`（只对 anthropic 有意义）：`key` → 只发 `x-api-key`（对应 cc-switch 的 `ANTHROPIC_API_KEY`）、`token` → `Authorization: Bearer`（对应 `ANTHROPIC_AUTH_TOKEN`）；BIOS 构造客户端时临时隔离 `ANTHROPIC_API_KEY` / `ANTHROPIC_AUTH_TOKEN` 环境变量，避免把机器上别的工具的 Key 发给提供商。**Base URL 归一**：anthropic 的 SDK 自己拼 `/v1/messages`，所以存之前去掉结尾的 `/v1`（`Providers.normalize_base`）。BIOS 按 kind 挂 `ai.responses` / `ai.chat.completions` / `ai.messages`，`Provider/Adapter.py` 的代理按配置动态选方言。界面「设置 → 模型」是 cc-switch 式两步添加：预设画廊（搜索名称/网址 + 左侧分类栏 + 分组双列卡片 + 自定义配置；141 条预设的地址、协议、认证方式、模型清单和图标照抄 cc-switch MIT，见 `说明/第三方许可.md`）+ 表单；支持「获取模型」（`/api/provider/models`，只在端点未变时复用已存 Key，避免 Key 被发到任意地址）、复制、设为当前、删除（当前使用的不能删）。**模型浮层列出所有已配置提供商的模型（按提供商分组）**，点哪个就切到对应的提供商 + 模型。**轮次中切换**：当前流仍用旧模型解析，下一次模型请求才用新模型；跨协议切换会先确认，且 `ModO` / `Summary` 在流开始时快照方言，不会用新解析器读旧流。切完 Spirit 重建客户端，下一轮生效。Key 明文写 `config.json`——该文件已加入 `.gitignore`。

**供应商管理全量（2026-11-19，照抄 cc-switch 3.18 的体系）**：数据模型在原有字段上补了 `notes` / `icon` / `icon_color` / `category`（official / cn_official / aggregator / third_party / cloud_provider / custom）/ `endpoints`（端点候选，`base_url` 永远排第一）/ `api_key_url` / `in_failover_queue`。新能力：

**OpenCode Go 网关要求（2026-11-19 实战修复）**：`opencode.ai` 的网关要求客户端 ① 报**自己的 User-Agent**（不能是 SDK / HTTP 库默认名，否则 403）② 每个会话带**稳定的 `x-opencode-session`**（不带 → `400 MissingSessionID`）。Spirit 直连没有代理层，所以由适配层自己补：

- `Config/Providers.py::is_opencode(base_url)` / `opencode_headers(session)`：UA = `Spirit/0.1.0`，session 由调用方给。
- `Provider/Adapter.py`：三种方言（Responses / Chat / Anthropic）在目标是 opencode 网关时，给 `create()` 加 `extra_headers`；session id = **第一条用户消息的 sha256 前 32 位**（`spirit-…`）。不拿系统提示词做指纹——Spirit 每轮会注入运行时上下文（工作目录 / 日期 / 待办），那样 id 会每轮变。压缩（摘要）后第一条用户消息被替换时，id 会变一次，可接受。

**工作区**：`engine.workdir` 当前、`engine.default_workspace` 默认、`engine.workspaces` 用户加的列表。`Engine.workspaces()` / `add_workspace(path)` / `select_workspace(path)`；切换后能力体系立即重绑，下一轮工具调用就在新目录。会话目录仍由数据根决定（`session_dir()`），界面只展示 / 打开。

### 健壮性（2026-11-19 批 C/D）

- **配置**：解析失败 → 坏文件改名 `config.json.corrupt-<时间>` 留档 + `degraded` 标记，不再"静默回默认再被覆盖"；每次成功保存前留一份 `config.json.bak`；旧扁平配置（没有 `providers`）不再被 DEFAULTS 里的示例 providers 盖住，`kind` 按 `llm.provider` 推导；启动时用 `Providers.sync_active()` 把顶层 `llm.*` 和当前提供商对账。
- **会话**：加载时逐行容错，坏行跳过并计数；`/api/session` 返回 `warnings`，界面提示"跳过 N 行损坏记录"。
- **请求**：SDK 自带重试关闭（`max_retries=0`）、统一超时 `llm.timeout`（默认 120s）；Reconnect 的退避等待可被"停止"打断。**503（上游维护 / 暂时不可用）最多重试 3 次**，然后直接给“模型服务暂时不可用（HTTP 503），已重试 3 次；请稍后再试或切换模型”，不再拖 5 次约 20 秒；其它可重试错误仍是 5 次。
- **故障转移**：当前提供商已熔断时，**请求前**就换下一家（不再先白打一轮）；仍不自动回切（避免抖动）。
- **用量**：价格支持 `cached_input`（不填按输入价）；聚合按币种分桶，`mixed` 标记跨币种会话；界面按币种显示 `¥/$`。
- **文件**：写文件 `newline=""`（Windows 不再 LF→CRLF）；读文件分块读到上限，不再整文件进内存。

### 外部审查修复（2026-11-19 批 R）

五组外部审查报的堵塞 / 安全缺陷，逐条核对后修了这些：

- **S2 ReDoS**：`searchFiles` 改用 `regex` 模块，每行 0.05 秒超时；灾难性回溯返回“正则匹配超时”，不再占死线程（新增依赖 `regex`）。
- **S3 replaceInFile**：2MB 上限、负数 `occurrence` 拒绝、写回 `newline=""`（不再把 LF 转 CRLF）。
- **S4 SSRF**：`fetchUrl` 拒绝私网 / 回环 / 链路本地 / 保留地址，能识别十进制、十六进制、八进制 IP；重定向每一跳都重新校验。
- **S5 命令替换**：`echo $(rm -rf …)` / 反引号里的命令递归过灾难闸，不再靠 `echo` 豁免。
- **S6 编码执行**：`powershell -e / -ec / -enc / -EncodedCommand` 一律拒绝。
- **S7 Git Bash 路径**：命令里的 `/c/...`、`/mnt/c/...` 先归一再匹配机器数据保护，`cat /c/.../config.json` 会被拒绝。
- **S8 失败流**：`response.failed` 抛 `ProviderStreamError`，不再伪装成成功；熔断 / 故障转移能正确记账，`response.incomplete` 标记截断。
- **内存 worker**：单条写失败不再打死 worker，`flush` 不会永久等。
- **熔断状态**：加锁，Web 的 `snapshot()` 与 CPU 的 `record()` 不再并发改 dict。
- **POSIX 进程组**：bash / 后台进程 `start_new_session=True`，`killpg` 不会误杀引擎自己。

**第二批（2026-11-19 批 S）**：
- **S1 缓解**：超时 / 取消后**换一个执行池**（`CapabilitySystem.__pool_recover`），旧池的僵尸线程不再堵死后续调用；线程仍然杀不掉，真正的进程隔离仍留作下一层。
- **S9**：会话切换 / 新建 / 轮次启动共用 `SESSION_LOCK`；轮次中切换直接拒绝，不再有"检查通过后轮次起飞"的窗口。**2026-11-20 修正**：锁只在输入体系真正读到消息时接管、CPU 轮末释放；阻塞等用户输入时不再占锁，否则空闲状态下新建 / 切会话会一直 409。
- **取消真正中断读流**：`ModO` 旁路线程发现取消就关流，模型流卡住时不用等 HTTP 超时。
- **故障转移总时限**：`engine.failover.total_timeout`（默认 180 秒），超了不再换家。
- **核对后不成立**：config.save 的 fsync / 重试发生在锁外（锁内只做快照），不会卡住其他配置读写。
- **仍留**：能力进程隔离（S1 的根治）、WSL 子进程收尾、Capabilities→Memory 的直接 import、架构依赖测试。

## 十一、扩展指南

### 加一个能力

1. 写一个类：`spec() -> CapabilitySpec` + `run(arguments) -> str`
   - `side_effect` 按实际行为声明：纯读 `"read"`、访问外部网络 `"external"`、会改东西 `"write"`（默认）。声明成 `read` 会跳过审批并允许批内并行，别乱写
2. 可选：`configure(config)` / `setup(deps)` / `dispose()`
3. 登记：`Engine.register_capability(MyCapability())`；或写进清单 JSON，用 `capabilities.load_manifest(path)`
4. 执行 / 校验 / 截断 / spill / 写表由能力体系统一做

### 加一个体系

1. 先过体系总表的归属判据：它是主体系，还是谁的子体系
2. 需要控制 → 在 `Bus/keys.py` 加 key，CPU 注册 / 读取
3. 异常 → `faults.for_system("名字")`
4. 不 import 兄弟主体系；需要读表就读数据表，需要交流就经 CPU

### 加一个 provider

1. 在 `Provider/Adapter.py` 新增一个类，实现 `LLMAdapter` 的方法（现有 `ResponsesAdapter` / `ChatAdapter`）
2. `get_adapter(kind)` 里返回它；配置里 `kind` 写同一个值，`Provider/Adapter.py` 的代理会动态切换
3. 保留 provider 的 opaque 字段（如 Anthropic 的 `signature`），不要归一化
